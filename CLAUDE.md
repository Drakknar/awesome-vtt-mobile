# awesome-vtt-mobile – project notes

Phone companion for Foundry VTT **v14** and **dnd5e 6.0.x** (built against 6.0.5, verified with 6.0.6), by Stefano Pignataro.
Sister module: `../awesome-vtt` (table mode).

## What it is
- **Users:** each player logs in as their **own user on their phone**, never the shared Table account. Their own login keeps whispers and GM rolls private.
- **Input:** touch-first, with buttons at least 44 px tall.
- **Phone mode:** a per-device setting. "Ask on phones" asks once on touch devices with a small screen.
- **No map:** by default phone mode turns on core No-Canvas mode (`core.noCanvas`), so the map isn't shown. The module only turns it off again if it turned it on (`managedNoCanvas`).
- **Layout:** turn banner and combat strip at the top; views (the Character tab's section tabs at its bottom); the quick actions sheet (one of the exclusive bottom sheets, with the switcher and the use dialog: `state.overlay`) (death saves at 0 HP, inspiration, rests, damage/heal/temp HP, concentration, exhaustion, quick conditions, toggleable effects; data from `getQuickActions` in the shared dnd5e adapter); the character pill (launcher button, switcher chevron, ADV/DIS chip); the tab bar below it. Commands go near the bottom, in thumb reach. The advantage choice is app-level (Dice tab) and one-shot.
- **Tabs:** Character, Dice, Chat, Journal, Compendium and Settings, all drawn by the module. Chat uses `ChatMessage#renderHTML` for each message (dnd5e listeners come with it), `ui.chat.processMessage(text, { speaker })` to send, and the core `messageMode` setting with `CONFIG.ChatMessage.modes`. Foundry's sidebar is never shown or touched: calling `ui.sidebar.expand()` at startup crashed on Firefox for Android (`chatControls is undefined`). The turn banner and combat strip sit at the top.

## Decisions agreed with the user
- **Keep the modules in sync (standing rule from the user):** every time something is added, removed or changed in the table or phone module, do the same in the other one through `awesome-vtt-core` (shared logic there; only templates, CSS, UI text and device-specific layout per module). If it's unclear whether or how a change applies to both, ask the user first.
- **Independent of the table module.** It requires only the library `../awesome-vtt-core` (dnd5e data, rolls and checks, compact sheet data and actions, dice pool, compendium and journal panels, chat / notice / busy-button helpers, journals, keep-screen-on; imported by relative path; see its CLAUDE.md for what belongs there), and adds physical dice when awesome-vtt is active. This module's own language prefix is `AVTTM.`; the core's is `AVTTC.`
- **Character tab:** only the module's own compact view. There is no full-sheet button, no Tidy5e integration and no Level up / Hero Mancer integration (the user dropped them: those UIs aren't made for phones). Levelling up is done from a computer.
- **Settings in two places:** every option is registered with `config: true`, so it appears both in the phone's Settings tab and in Foundry's settings window.
- **Using activities (`use.mjs`):** tapping an item opens a bottom-sheet dialog only when needed: choose activity (several) → targets (`needsTargets`: attack/save types, a template, or `target.affects.type` of ally/enemy/creature/…) → roll options (attack: mode, bonus, attack mode, ammunition, mastery; damage/heal: bonus). The choices reach dnd5e through `dnd5e.preRollAttackV2` / `dnd5e.preRollDamageV2`, matched to the activity or its item (for cast/forward activities), used once, with `dialog.configure = false`. A "usage" (Casting) step replaces dnd5e's usage dialog: `usageOptions` reads dnd5e's defaults (`_prepareUsageConfig`, `_requiresConfigurationDialog`) and slot list; `usageFor` builds `activity.use(usage, { configure: false })`. Measured templates are always off while the map is off (they made the use hang/need double taps). Cast and forward activities are resolved first (`resolveActivity`: the cast spell, created like dnd5e does, or the target activity, with dnd5e's `cause`). The step also covers linked spell levels and linked resources, non-spell scaling, and enchant / summon (profile, size, type) / transform profiles, with labels from dnd5e's own dialog class (`metadata.usage.dialog.prototype.getProfileLabel`). Summon placement is off while the map is off. Only uncovered activity types (e.g. bastion "order") keep dnd5e's dialog.
- **Targets without the map:** the phone wraps `dnd5e.dataModels.chatMessage.fields.TargetsField.getDescriptors` (only for calls without arguments, while there's no canvas) and sends targets with `game.user.broadcastActivity({ sceneId, targets })`.
  - No line-of-sight check; the GM limits the list with the "Phone target list" setting.
  - Names follow token nameplate visibility.
- **Your-turn alert:** stays silent when core's Combat Theme already plays turn sounds.
- **Automation:** optional prompts, one client setting each, all off by default: `autoDeathSaves`, `autoConcentration`, `autoSaves`, `autoRequests`, `autoInitiative`. The core's `prompts.mjs` builds them from dnd5e's own data (shared with the table, which has the same settings). Concentration comes from dnd5e's "prompt" message; saves from "usage" messages of save activities with `system.targets`; GM requests from "request" messages handled by `CONFIG.DND5E.requests[handler]`; initiative (one prompt per character, with a roll mode) and death saves from the active combat. Initiative everywhere (combat strip and prompts) uses the core's `rollInitiative(actor, mode)`, the same as the table: no dnd5e dialog, the Next roll choice, the shown character only. The app queues them (`app.prompts`, a core `PromptQueue`), shows one at a time as the "prompt" bottom sheet, and rolls through the shared adapter the same way dnd5e's buttons do. Answering or skipping sends `promptDone` on the core's socket, so the same prompt closes on the player's other devices.
- **Sections:** the tab bar's views are the core's `SECTIONS` plus Settings, with the core's icons; the table's section bar uses the same list. The advantage model here (one Next roll choice, chip on the pill, reset after one roll) is also the table's, by the user's choice.
- **Busy buttons:** actions in `BUSY_ACTIONS` (app.mjs) disable their button until `#dispatch` resolves; add new submitting actions there.
- **Result notice:** `roll-toasts.mjs` uses the core's `onRollResult` + `rollNotice` for every roll message authored by this user (any dice; after Dice So Nice; blind rolls skipped), as the table's seats do (setting `rollToasts`, on by default). Because it is per user, a roll the same player makes on another device also shows here. **Roll damage button (user, 2026-10-10, both modules, all systems):** when the core's `offersDamage(result, autoDamage)` is true (summarizeRoll's `damage`: an attack/spell/action that didn't miss, unknown counts; not when the adapter auto-rolls it), the toast gets a sibling `.avttm-toast-action` button (`toastAction`, core `fillNoticeAction`; both inside the fixed `.avttm-toast-box`) running `sys.rollDamageFrom(message)`; toast then stays 30 s. SotDL spells / talents / items used without a roll get a `kind: "use"` notice (name only).
- **Tab bar:** a separate top-level element (`#avttm-tabbar`) with a z-index above all Foundry windows. Full-screen windows and bottom-sheet dialogs end above it (`--avttm-tabbar-height`). Tapping a tab closes full-screen windows but keeps DialogV2 dialogs and the RollResolver open, so a roll isn't cancelled or rolled digitally.
- **Home screen:** a manifest plus Apple tags; no service worker.
- **2026-10-04 batch (user's requests; only syntax-checked):** Spells tab (core `getSpells` / `spellPrepare`); damage rolled right after every attack roll (core `rollDamageAfterAttacks`, client setting `autoDamage`, default on; dnd5e only since 2026-10-10, the SotDL adapter does nothing); target highlighting while picking: each tap in the targets step calls `targets.previewTargets` (broadcasts `targets`, and for a newly picked token `cursor` at its centre + `ping: { scene, style: "pulse" }` + `levelId`; cursor cleared after 1.5 s), and closing the dialog without use calls `restoreTargets()`; Party tab when the optional `../awesome-vtt-shared-inventory` module is active (`views()` in constants.mjs is now a function, read after ready), `invToParty` inventory button.
- **Favorites (user, 2026-10-04, like the table):** stars on Actions / Spells / Inventory rows (`toggleFavorite`, core); tapping the pill's portrait (a button with a ☆ badge; a separate button squeezed the info area too much, user 2026-10-04) (`toggleFavorites`, client setting `favoritesOpen`) shows a sideways-scrolling row of `getFavoriteActions` below the pill (`.avttm-top` wraps). The phone pill doesn't fold, so the portrait toggle stands in for the table's unfolding.
- **Table seat (user's request, 2026-10-04):** the Settings tab shows "Table seat" for the shown character when the table module is active, using its `api` (`seatOptions`, `moveSeat`; see `../awesome-vtt/CLAUDE.md`); re-rendered on `awesome-vtt.seatsChanged`.
- **Shadow of the Demon Lord (phase 1, 2026-10-04):** through the core's `system.mjs`; without `sys.FEATURES.useSteps` (SotDL) tapping an item uses it straight away (`#d20` + `sys.useItem`), and `initTargets` / `registerUseHooks` (dnd5e) aren't installed; the combat strip shows Fast / Slow; templates read the adapter's `stats`, `rests`, `tracks`, `deathSave`, roll-mode `text` / `tone`.
- **SotDL phase 2 (2026-10-04):** `#startItemUse`: items where `sys.itemNeedsTargets` open the use dialog with `state.use.simple` (steps targets (if the target list is on) → options: boons/banes + whole-number modifier, `MODIFIER`), `#performItemUse` → `sys.useItem(actor, id, mode, { targets: targets.selectedTokens(), modifier })`; other items use straight away. `initTargets()` runs in every system (dnd5e bridge only in dnd5e). Prompts, favorites and the Party tab come from core / the shared inventory module.
- **SotDL without the map (2026-10-10, user's bug report: talents failed with "canvas.tokens is undefined"):** the system's TokenManager reads `canvas.tokens` (controlled / placeables) and `game.user.targets`. `installDemonlordBridge()` (targets.mjs, only with core No-Canvas on) defines a stand-in `canvas.tokens` (no placeables; `controlled` = the phone's targets when the system's "target on select" is on) and copies the phone's targets into `game.user.targets` as token-like objects (`id`, `name`, `document`, `actor`, `center`) without core's `targetToken` hook (its SotDL handler measures on the map). Talents and gear that attack now ask for targets too (core `itemNeedsTargets`). SotDL card buttons that read targets (`.roll-damage`, `.apply-damage`, `.roll-healing`, `.apply-effect`) in the Chat view, and the toast's Roll damage, first open a targets-only use dialog (`app.askCardTargets`; a pick is a `state.use` with `resolve`), only when the adapter has `CARD_TARGET_BUTTONS` and the map isn't shown. Phone-only: the table has the map. Only syntax-checked.
- **Out of scope for now:** Actor Studio and Pixels support.

## Upstream watch

`.github/workflows/compat-review.yml` runs daily and has Claude review this module once for each new version of a dependency, following `.github/prompts/foundry-compat.md`.
- **Game systems:** a release of a system in `relationships.systems` newer than its `verified` version.
- **Foundry core:** a new Stable build, with a light review within the verified generation and a full review for a new generation.
- **Results:**
  - The module is fine: a pull request that bumps `verified`. It goes out with the next manual release.
  - A fix: a pull request.
  - Anything that needs the owner: an issue labelled `upstream-watch` and assigned to the owner.
  - New features worth using: an `enhancement` issue.
- **Access:** Claude works with read-only access (secret `CLAUDE_CODE_OAUTH_TOKEN`). A separate job opens the pull request and issues.
- **Isolation (tested 2026-10-11):**
  - **Before Claude runs:** the review job turns on the action's subprocess secret scrub and installs bubblewrap, so Claude's commands don't see the Claude token or any other process. It also blocks reading other processes' memory and removes sudo, and Docker is switched off (Docker access amounts to root).
  - **After Claude:** the steps that follow ignore variables and PATH entries its commands could plant, and make the diff in a fresh clone.
  - **Publishing:** the report job won't publish output that contains the token, or a piece of it, and deletes the review's artifact.
  - **What's left:** Claude's commands never see the token, so leaking it would take a way around the sandbox. The scan is a second line of defence.
- **Bookkeeping:** `.github/scripts/watch.sh` records what was reviewed on the `watch-state` branch. Run the workflow by hand with `force` to review again.
